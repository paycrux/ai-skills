# flow 스킬 — 구조 변경안 (2026-10-23)

> 읽고 합의하면 `handoff.md`의 결정 표에 옮기고 구현을 시작한다. 합의 전에는 코드를 고치지 않는다.

## 1. 왜 바꾸나

지금 `flow`는 작업마다 HTML 페이지 6~7장을 만들고, 사람이 페이지에서 답하면 브라우저가 `data/inbox.json`에 쓰고, Claude가 `build.py apply`로 반영한다. 써 보니 네 가지가 막혔다.

| 문제 | 실제로 본 것 |
|---|---|
| 폴더 연결 | 브라우저는 `file://` 페이지가 파일을 쓰지 못하게 막는다. 그래서 사용자가 매번 폴더를 고르고 허용해야 했다 |
| 페이지 이동 | 단계마다 페이지가 따로라서, 04 구현 계획의 `SOT: 5–9`를 확인하려면 02로 넘어가 행을 찾고 다시 돌아와야 한다 |
| 문서가 흩어짐 | example-app의 `docs/`에는 폴더 75개가 한 층에 있다. 선물하기 하나가 `gift` · `gift-bugs` · `gift-tab-followups` · `gift-bottom-inset` · `gift-receiver-phone-format` 다섯 폴더로 나뉘어 있다 |
| 깨진 참조 | 26개 파일이 `/Users/me/workspaces/example-app/APP-363/docs/...` 같은 다른 워크트리 절대 경로를 가리킨다. 그 워크트리들(APP-357 · 358 · 361 · 363 · 372 · 489)은 이미 지워져서 링크가 전부 죽었다 |

앞의 두 가지는 "브라우저가 파일을 쓸 수 없다"는 한 가지 사실에서 나왔다. 그걸 피하려고 inbox, apply, 페이지별 목록 생성을 덧붙이면서 구조가 복잡해졌다. 뒤의 두 가지는 폴더를 작업 단위로 만들고, 경로로 참조한 데서 나왔다.

## 2. 바꾸는 결정

| 항목 | 지금 | 바꾼 뒤 |
|---|---|---|
| 보는 방법 | 작업마다 HTML 6~7장, 더블클릭으로 열기 | 로컬 서버 하나 + 공용 뷰어. `npm run flow`로 켬 |
| 데이터 | `data/sot.json` · `data/grill.json` + Claude가 직접 쓰는 HTML 4장 | 도메인의 `screens.json` + 작업마다 `tasks/<작업 ID>.json`. HTML은 저장하지 않음 |
| 사람이 저장 | 폴더 연결 → `inbox.json` → "저장했어" → `apply` | 페이지에서 저장 → 서버가 그 작업의 json에 바로 씀 |
| Claude가 읽기 | 앞 단계 결론 블록 + 현재 페이지 | 현재 작업 json + `screens.json`. 사람이 바꾼 곳은 `git diff` |
| 동시 수정 | 막는 장치 없음 | 서버가 파일 지문(해시)을 비교해, 그 사이 바뀌었으면 저장을 거부하고 새로고침을 안내 |
| 폴더 단위 | 작업 하나 = 폴더 하나 | 도메인(화면 묶음) 하나 = 폴더 하나. 작업은 그 안의 파일 |
| 단계 사이 이동 | 페이지 이동 | 한 페이지 안에서 스크롤. 왼쪽 목차 |
| 도메인 사이 이동 | 없음. 폴더를 직접 찾아 열기 | 모든 페이지 왼쪽에 `docs/` 전체 도메인 목록. 어디서든 다른 도메인으로 바로 이동 |
| 참조 | 글자(`SOT: 5–9`, `3 · 질문 R2`) | 링크. 마우스를 올리면 내용 미리보기, 누르면 그 자리로 이동 |

유지하는 것

- 문서는 각 브랜치의 `docs/` 아래에 두고 코드와 함께 커밋해서 PR에 들어간다(전역 규칙 그대로)
- 단계 흐름 01 기획 → 02 화면 · SOT 맵 → 03 질문 → 04 구현 계획 · 구현 → 05 검증 → 06 완료, 필요한 단계만 만들기
- 단계마다 맨 위 결론, SOT 분류(서버 그대로 / 앱 가공 / 동작 / 미정 / 범위 제외), 화면 밖 상태
- 디자인 기준(바젤 그리드, 흑백, 번호에만 색)
- 레거시 문서와 레거시 스킬(`task-plan` 등)은 손대지 않는다

## 3. 폴더 구조

```
<프로젝트>/
├ package.json                   "scripts": { "flow": "node docs/.flow/server.mjs" }
└ docs/
  ├ .flow/                        flow 공용. 커밋됨
  │ ├ server.mjs                  의존성 없는 Node 서버
  │ └ viewer/                     뷰어 HTML · CSS · JS
  ├ gift/                         도메인: 선물하기
  │ ├ domain.json                 도메인 이름, Figma 섹션 · 노드 ID, 화면 파일 경로 (새 작업이 이 도메인인지 찾는 기준)
  │ ├ screens.json                화면들의 SOT 맵. 항상 지금 기준의 최신 상태
  │ ├ tasks/
  │ │ ├ APP-451.json              기프트샵 · 선물 결제
  │ │ ├ APP-452.json              선물내역
  │ │ └ bug-bottom-inset.json     지라 키가 없는 작업은 짧은 영어 이름
  │ └ images/                     Figma 스크린샷 · 구조 XML
  ├ gift-bugs/plans/tasks.md      레거시. 그대로
  └ …
```

- 서버 코드는 저장소에 복사해서 커밋한다. 스킬이 없는 팀원도 Node만 있으면 `npm run flow`로 볼 수 있다. 스킬을 업데이트하면 다음 `init` 때 다시 복사한다
- `package.json`이 없는 프로젝트는 `node docs/.flow/server.mjs`를 직접 실행한다
- `package.json`에 스크립트 한 줄을 넣는 것은 공유 저장소 변경이다. 프로젝트에서 처음 넣을 때 팀에 알린다

## 4. 서버와 뷰어

| 주소 | 보이는 것 |
|---|---|
| `/` | `docs/` 전체 트리. flow 도메인은 진행 중인 작업과 단계 상태까지, 레거시 `.md` · `.html`은 파일 링크 |
| `/gift/` | 도메인 페이지. 위에 화면과 SOT 맵, 아래에 작업 목록(진행 중이 위, 끝난 작업은 접힘) |
| `/gift/APP-452` | 작업 페이지. 01~06을 한 페이지로, 왼쪽에 단계 목차 |
| 레거시 파일 | `.html`은 그대로 열고, `.md`는 읽기 좋게 그려서 보여 줌. 읽기 전용 |

왼쪽 내비게이션 — 모든 페이지에 같은 것

```
example-app · feat/APP-452        ← 이 서버가 보여 주는 저장소와 브랜치
[ 찾기… ]
도메인
  ▾ gift 선물하기
      화면 · SOT 맵
      ● APP-452 선물내역         진행 중
      ● APP-533 후속             질문 대기
      ▸ 끝난 작업 3
  ▸ coupon 쿠폰
  ▸ product 상품
레거시 문서 72                                ← 접혀 있음
```

- 서버가 켜질 때와 페이지를 열 때마다 `docs/`를 훑어서 만든다. 손으로 맞추는 목록이 없다
- `gift` · `coupon` · `product` 어느 페이지에 있든 같은 목록이 보이고, 다른 도메인으로 바로 넘어간다. 지금 보는 곳은 강조된다
- 작업 페이지 안에서는 목록 아래에 그 작업의 단계 목차(01~06)가 붙는다
- 찾기 칸은 도메인 · 작업 ID · 화면 이름 · 레거시 파일 이름을 거른다

서버를 여러 개 띄울 때

- 서버 하나는 자기가 실행된 워크트리의 `docs/` 하나만 보여 준다. 워크트리가 여럿이면 Claude가 워크트리마다 서버를 띄울 수 있다
- 포트는 기본값이 쓰이고 있으면 빈 포트를 찾아 쓰고, 터미널에 주소를 출력한다
- 어느 서버를 보고 있는지 헷갈리지 않도록 내비게이션 맨 위와 브라우저 탭 제목에 저장소와 브랜치를 표시한다
- 같은 워크트리에 서버가 이미 떠 있으면 새로 띄우지 않고 그 주소를 다시 쓴다. 떠 있는 서버의 포트는 그 워크트리의 git 폴더(`git rev-parse --git-dir`, 커밋되지 않음)의 `flow-server.json`에 적는다
- 서버가 쓰는 곳은 flow 도메인의 json 파일뿐이다. 레거시 파일과 그 밖의 경로에는 쓰지 않는다
- flow 도메인인지는 폴더에 `domain.json`이 있는지로 구분한다. example-app의 레거시 문서에는 해당 파일이 없다

저장과 충돌

1. 페이지를 열 때 서버가 json 내용과 그 지문을 함께 준다
2. 사람이 답 · 체크 · 수정을 하고 저장하면, 페이지가 바뀐 json과 처음 받은 지문을 보낸다
3. 서버는 지금 파일의 지문과 비교해서, 같으면 쓰고 다르면 거부한다. 거부되면 페이지가 "Claude가 먼저 고쳤어요, 새로고침"을 보여 준다
4. 저장 전 내용은 브라우저 저장소에도 남겨 두어서, 거부되거나 서버가 꺼져 있어도 고친 내용이 사라지지 않는다

Claude 쪽

- Claude는 json을 직접 고친다. 서버를 거치지 않는다. 사람이 페이지를 열어 둔 사이 Claude가 고쳤다면 위 3번에서 걸린다
- 사람이 저장한 뒤 채팅에 알려 주면 Claude가 `git diff docs/<도메인>/`로 바뀐 곳을 본다
- 고친 답처럼 Claude가 처리해야 하는 항목은 서버가 `"by": "user"` 표시를 남긴다. Claude가 처리하면서 지우고, `check`가 남은 표시를 잡는다

## 5. 도메인 규칙 — 문서가 늘어나지 않게

- 새 작업을 시작하면 먼저 기존 도메인에서 찾는다. 기준은 `domain.json`의 Figma 노드 ID, 화면 이름, 화면 파일 경로
- 찾으면 그 폴더의 `tasks/`에 파일만 추가한다. 출시된 기능의 후속, 버그, 문구 수정도 같은 폴더다
- 새 폴더는 새 도메인일 때만 만든다. 도메인 하나는 Figma 최상위 섹션 하나(선물하기, 계정 설정, 주문서)다. 화면이 없는 작업(빌드, 배포)은 주제마다 하나
- SOT 맵은 도메인에 하나다. 작업은 바꿀 행을 고치고, 그 행에 작업 ID를 남긴다
- Claude는 현재 작업 파일과 `screens.json`만 읽는다. 끝난 작업은 읽지 않으니 도메인이 커져도 읽는 양은 그대로다

작업마다 파일을 따로 두는 이유: 같은 도메인의 작업 두 개가 서로 다른 브랜치에서 동시에 진행되면, 파일 하나를 함께 고칠 경우 루트에 합칠 때마다 git 충돌이 난다. 작업별 파일이면 각 브랜치는 자기 파일만 추가한다. `screens.json`의 같은 행을 두 작업이 동시에 고칠 때만 충돌이 나는데, 이건 실제로 같은 화면을 동시에 바꾸는 경우라 사람이 봐야 하는 충돌이다.

전역 규칙과의 관계: `~/AGENTS.md`의 "Merge Into an In-Flight Plan"에는 출시된 기능을 고칠 때 새 폴더를 만들고 `참조:` 링크를 다는 패턴이 있다. flow에서는 위 규칙을 따른다. 레거시 스킬 쪽 규칙은 그대로 둔다.

## 6. 참조 ID

| 대상 | ID | 예 |
|---|---|---|
| SOT 행 | `S` + 번호 | `S5` |
| 화면 밖 상태 | `X` + 번호 | `X3` |
| 질문 | 작업 안에서 라운드-질문 | `R2-Q1` |
| Phase · 항목 | `P` + 번호 | `P2` |
| 버그 | `B` + 번호 | `B1` |
| 다른 작업의 항목 | 작업 ID 앞에 붙임 | `APP-451#R2-Q1` |
| 다른 도메인 | 도메인 앞에 붙임 | `login/S3` |

- 번호는 한 번 붙이면 바뀌지 않는다. 지운 번호는 다시 쓰지 않는다. 행을 중간에 넣어도 기존 참조가 밀리지 않는다
- 경로 대신 ID로 참조하니, 폴더를 옮기거나 워크트리가 지워져도 링크가 깨지지 않는다
- 반대 방향 참조도 보인다. SOT 행 옆에 "APP-452 P2에서 씀"이 붙는다(뷰어가 계산하고, 파일에는 쓰지 않음)
- 레거시 문서를 가리킬 때는 경로를 그대로 쓴다

## 7. 없어지는 것 / 남는 것

| 없어짐 | 남음 · 새로 생김 |
|---|---|
| `build.py`의 `build` · `apply` · `tick` · `add` | `init`(도메인 만들기 또는 기존 도메인에 작업 추가, 서버 · 뷰어 복사, `package.json` 스크립트), `check`(json 형식 검사, 처리 안 한 `"by": "user"`) |
| `inbox.json`, "반영 대기" 표시 | `server.mjs`, `viewer/` |
| 단계 페이지 템플릿 4개, 페이지별 목록 생성, 결론 블록 정규식 | json 스키마 하나(도메인 · 화면 · 작업) |
| `live.js`의 폴더 연결 | 뷰어의 저장 · 충돌 안내 |
| `merge-xml` | 남김. Figma 컴포넌트 안쪽 좌표를 합치는 일은 그대로 필요 |

작업 트리에 커밋하지 않은 변경이 있다(`live.js`의 docs 폴더 한 번 연결, `build.py`의 `--stages` · `add` 등). 이번 변경으로 대부분 쓸모가 없어지지만, 지우거나 되돌리는 건 따로 정한다. `SKILL.md`의 작업 크기별 시작 표, 긴 기획서 처리, `references/sot-map.md`의 섹션 분류는 새 구조에서도 그대로 쓴다.

## 8. 제약

- 서버 없이는 볼 수 없다. `file://` 페이지는 json을 읽지 못하기 때문이다. GitHub에서 json을 직접 읽는 것은 가능하다
- Node가 필요하다. RN · Next 프로젝트에는 이미 있다
- 저장은 서버가 켜진 동안만 된다. 꺼져 있으면 페이지가 바뀐 내용 "복사" 버튼을 보여 주고, 채팅에 붙여넣으면 Claude가 json에 쓴다
