# 제안: 스킬 조합 & 업데이트 드리프트 개선

**출처:** AI Skills 사용 피드백 관련 팀 Slack 스레드 (2026-07-01 취합)
**참여자:** 고현수, 정해수, 김하진, 엄문주

> 이 문서는 팀 논의에 한해 한글로 작성되었습니다 (예외 적용).

## 1. 피드백 요약

| 작성자 | 피드백 | 실제 니즈 |
| --- | --- | --- |
| 정해수 | `/task-plan` 하나만 실행하는 대신, 한 번의 요청에서 스킬을 조합하고 싶어함 — 예: "`/task-plan /ui-plan {기획서, 디자인 링크} ...`, QA 전용 프로젝트라면 UI 작업 제외, 바로 `/qa-guide`까지" | 스킬 조합 / 범위 제외(scoped exclusion) |
| 정해수 | `0.4.4`/`0.4.5` 경량화 업데이트 이후에도 여전히 예전(무거운) `task-plan` 산출물이 나옴 | 조용한 버전 드리프트 — 설치가 최신이 아님 |
| 김하진 | 복잡한 구현일 때만 스킬을 찾음. 가벼운 작업에서는 건너뜀 | 도입 장벽(adoption friction) |
| 김하진 | 설치가 `curl \| bash` 일회성 방식이라 업데이트를 놓치기 쉬움. 리모트를 확인하고 자동으로 pull하는 `SessionStart` 훅 제안 | 업데이트 확인 메커니즘 부재 |
| 엄문주 | 👍 (구체적 요청 없음) | — |

이 중 두 가지는 사실 같은 근본 원인입니다. 정해수의 "경량화가 안 됨" 이슈는 김하진이 지적한 문제와 **정확히 같은 상황일 가능성이 매우 높습니다** — `0.4.4`/`0.4.5` 배포 이후 로컬 설치에서 `--update`를 다시 실행하지 않았고, 새 버전이 나왔다는 사실을 알려주는 장치도 없었던 것입니다. 업데이트 가시성을 개선하면 두 문제가 동시에 해결됩니다.

## 2. 현재 아키텍처 (배경 정리)

- 스킬은 `.claude/skills/<name>/SKILL.md` 아래의 슬래시 커맨드이며, `curl | bash install.sh`로 설치됩니다. 데몬, 레지스트리, 오케스트레이터는 없고 각 스킬은 사용자 또는 `CLAUDE.md`의 라우팅 규칙에 의해 독립적으로 호출됩니다.
- `install.sh`는 `VERSION`(현재 `0.4.5`)을 하드코딩하고 있지만, 소비 프로젝트 어디에도 *실제로 어떤 버전이 설치되었는지* 기록되지 않고, 더 새로운 버전이 있는지 확인하는 로직도 없습니다. 사용자는 README를 다시 읽거나 공지를 봐야만 알 수 있습니다.
- `task-plan`은 `0.4.4`/`0.4.5`에서 의도적으로 경량화되었습니다. 이제 `tasks.md` + `spec.md`만 작성하며, 과거 별도 산출물이던 `README.md` / `ui-spec.md` / `progress.md`는 인라인 섹션으로 통합되었습니다. 별도의 `/ui-plan` 스킬은 존재하지 않습니다 — Figma 링크가 주어지면 UI-spec 내용은 이미 `task-plan` 산출물 안에 들어갑니다.
- 스킬 체이닝은 현재 비공식적으로 이루어지고 있습니다. 사용자가 한 프롬프트 안에 자유 형식 지시를 적으면(정해수가 이미 하고 있듯 — "GA 쪽은 UI 작업 필요없어서 제외해달라구 따로 부탁하고 `/qa` 어쩌구까지 포함시켜서 바로 생성") 에이전트는 관례적으로 이를 따르지만, 이것이 지원되는 동작이라고 명시한 스킬 문서는 없습니다.

## 3. 제안하는 개선 방향

### 3.1 업데이트 드리프트: 버전 스탬프 + `SessionStart` 체크 (최우선)

효과 대비 비용이 가장 낮은 개선입니다. 지금 실제로 혼란을 일으키고 있는 문제이기도 합니다.

- `install.sh`가 설치/업데이트 시마다 버전 마커 파일을 남깁니다. 예: `.claude/.ai-skills-version`에 설치된 버전 문자열만 기록.
- 스킬과 함께 `SessionStart` 훅을 배포하고(소비 프로젝트의 `.claude/settings.json`에 연결), 다음을 수행합니다:
  1. 로컬 버전 마커를 읽는다.
  2. GitHub의 원격 `install.sh`에서 `VERSION` 값을 가져온다 (가벼운 `curl`, 짧은 타임아웃, 오프라인 시 조용히 실패).
  3. 원격 버전이 더 최신이면, 세션 시작 시 정확한 `--update` 명령어와 함께 한 줄 안내를 출력한다.
- **자동으로 pull하지 않습니다.** 세션 도중 스킬 파일을 사용자 승인 없이 조용히 덮어쓰는 것은 공유되고 되돌리기 어려운 변경이므로, 알림만 띄우고 `--update` 실행은 사용자가 직접 하도록 둡니다. 다른 의존성 버전업과 동일한 방식입니다.
- 이 개선만으로 정해수의 "슬림화가 안 됨" 이슈가 해결됩니다. 드리프트를 조용히 틀리게 두는 대신 눈에 보이게 만드는 것이기 때문입니다.

### 3.2 스킬 조합: 이미 되는 것을 문서화하고 공식화

정해수가 이미 사용 중인 우회 방법 — 프롬프트에 UI 작업 제외를 요청하고 `/qa`를 덧붙이는 것 — 은 스킬이 하드코딩된 상태 기계가 아니라 에이전트가 해석하는 방식이기 때문에 이미 동작합니다. 문제는 이것이 어디에도 문서화되어 있지 않아 발견하기 어렵고, 일관되게 동작한다는 보장도 없다는 점입니다. `task-plan`이 방금 제거한 복잡성을 되살리지 않으면서 이 간극을 메우는 두 가지 변경을 제안합니다:

1. **`task-plan/SKILL.md`에 "범위 제외" 안내 추가.** `## Notes` 아래에 한 줄: 사용자 프롬프트에 제외 요청이 명시되면(예: "UI 작업 제외", "QA만 필요") 해당 Phase task를 건너뛰고, 별도 스킬이나 템플릿 분기를 만드는 대신 `tasks.md` 헤더에 제외 사항을 기록한다. 이렇게 하면 정해수의 애드혹 패턴이 문서화되고 검토 가능한 동작이 됩니다.
2. **`README.md`에 "스킬 조합" 섹션 추가.** 지원되는 체인 순서(`task-plan → implement → evaluate / qa → finalize`)와 정해수의 실제 사용 패턴과 일치하는 예시를 함께 제공합니다:
   ```
   /task-plan {기획서, 디자인 링크} 이 작업 진행하려고 해. UI 작업은 제외하고 QA 체크리스트까지 만들어줘
   ```
   QA 전용 플로우에는 이미 존재하는 하위 스킬인 `/qa-guide`, `/qa`를 연결 지점으로 명시해야 합니다. 정해수가 지금 수동으로 이어붙이고 있는 작업과 정확히 일치하기 때문입니다.

**권장하지 않는 방향:** 별도의 `/ui-plan` 스킬이나 새로운 오케스트레이션/워크플로우 엔진을 만드는 것. `task-plan`은 UI-spec 내용을 인라인으로 통합하기 위해 방금 경량화되었습니다. 같은 내용을 위한 병렬 스킬을 추가하면 그 작업이 무효화되고, `0.4.4` 리팩터링이 제거한 타입 분기가 다시 생겨납니다. 조합은 새로 유지보수해야 할 두 번째 시스템이 아니라, 프롬프트 레벨(스킬이 범위가 지정된 지시를 해석하는 방식)에 머물러야 합니다.

### 3.3 도입 장벽 (김하진)

지금 단계에서 구조적 변경을 제안하지 않습니다. 이는 독립적인 문제라기보다 3.1의 증상일 가능성이 높습니다(오래되었거나 신뢰할 수 없는 스킬 동작 때문에 신뢰도가 낮아져, "위험을 감수할 만큼 큰" 작업에서만 스킬을 찾게 되는 것). 3.1과 3.2가 반영된 뒤 재평가하고, 그래도 가벼운 작업에서의 도입률이 낮다면 별도로 조사합니다 (예: `CLAUDE.md`의 자동 프롬프트 트리거가 작은 작업에서 너무 쉽게 무시되는지 등).

## 4. 실행 순서

1. 버전 마커 + `SessionStart` 업데이트 체크 훅 — 지금 실제로 발생 중인 드리프트 문제를 해결
2. `task-plan` 범위 제외 안내 + README 조합 섹션 — 기존 애드혹 사용 방식을 공식화
3. 더 무거운 것(진짜 오케스트레이터, `--only` 조합 플래그 등)을 고려하기 전에 한 스프린트 동안 실제 사용 패턴을 지켜봅니다. 팀의 현재 패턴 — 한 프롬프트 안에서 평문 지시로 스킬을 잇는 것 — 이 이미 제기된 케이스들을 커버하고 있으므로, 두 번째 구체적 니즈가 나오기 전에 미리 도구를 만들지 않습니다.
